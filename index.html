How I work

Approach

01

Metrics before models

Agree on the business metric and the evaluation metric that tracks it before touching a model. Fraud at 0.17% prevalence is an AUPRC problem, not an accuracy problem; a loan model is judged at its operating threshold.

02

Monitoring is part of the model

A model ships with its drift checks, alert thresholds and retraining trigger, not after. Evidently, CloudWatch and Prometheus are in the first PR, not the last.

03

Reproducible by default

Versioned data (DVC), tracked experiments and a registry (MLflow), pinned environments, and CI that runs the tests. If a result cannot be rebuilt from the repo, it is not done.

Writing

Notes

Brief write-ups drawn from the projects above.

Evaluation

Why AUPRC, not ROC-AUC, for 0.17% fraud

At 0.17% fraud in 284,807 transactions, ROC-AUC stays flattering even when precision collapses, because the huge negative class dominates the false-positive rate. Precision-recall is the curve a fraud-ops team actually lives on, so the fraud pipeline selects and tunes models on AUPRC. See fraud-detection-mlops.

Monitoring

Drift reports as a CI artifact

In the sentiment platform, Evidently drift reports sit next to the Prometheus/Grafana runtime metrics and the GitHub Actions test suite, rather than being a separate notebook someone remembers to run, the point is that a distribution shift is visible before it becomes a quality incident. See financial-sentiment-mlops.

Retrieval

Graph + vector retrieval for structured domains

University data has explicit relationships (program → department → requirement) that pure embedding search flattens. The chatbot pairs a Neo4j graph lookup with OpenAI-embedding similarity so answers can be grounded in both the structure and the text. See RAG-Chatbot-1.
